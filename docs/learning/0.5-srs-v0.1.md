> **Phase:** 0 · **Kind:** docs · **Commit:** `step(0.5): write SRS v0.1 — 66 functional and 33 non-functional requirements traced to goals and scheduler rules` · **Date:** 2026-09-21

## What was done

[srs.md](../deliverables/srs.md) → `out/Srs.docx`: nine sections, ~5,000 words, 23 tables.
Five actors; eleven use cases with surface, pre- and postconditions and the alternatives that
matter (UC-07a template story; UC-11 parent assistant); **66 functional requirements** in seven
capability groups (`FR-CUR`, `FR-LRN`, `FR-TUT`, `FR-CNT`, `FR-SPC`, `FR-RPT`, `FR-AI`) and
**33 non-functional** ones (safety, privacy, offline, performance, cost, i18n, accessibility,
device floor, reliability, observability, explainability, testing); the AI capabilities as seven
**ports**; two traceability tables (goals → requirements, use cases → requirements); a glossary.
Every requirement has a priority and a source — a goal `G-n`, a scheduler rule `R-n`, a
principle, a use case or a step.

## The mental shift

A requirement is only real if it can fail. "The app shall be fast" cannot; "≤ 100 ms at p95 on a
2019 mid-range device" can — and the moment I wrote numbers I did not yet have, I needed a rule
for them, so *planning value* was born: a number with the experiment that owns it written next
to it. That turns the study phases into something sharper than exploration: A3 has a compliance
rate to reach, B3 a floor to find, E3 a cost line to stay under. The second shift is that the
non-goals from the charter became some of the most testable requirements in the document —
"no illustration is generated", "no free-form child input reaches a model" are single assertions.

## Gotchas hit

- The surface-split question (parent screens inside the child app or on the web) had been asked
  and not yet answered; the spec needed an answer to assign surfaces to use cases. It is written
  as **proposed decision D-2026-09-21-8** with its rationale, so reversing it is one revision,
  not a rewrite.
- Nine planning values were invented in one sitting (cost per child-day, pack size, three
  latencies, batch window, device class, canvas size, recording time-to-live). Each is tagged
  *(planning)* with its experiment; none should be quoted as a fact until measured.
- `FR-AI-001` first cited a guardrail as if it had a `P-` number; it does not (it is a PLAN §6
  rule). Fixed the citation — sources must be things that exist.
- Tables held at four columns after 0.4b's lesson on Word portrait width; the use cases became
  prose blocks instead of a table for the same reason.
- ~5,000 words — the largest document so far; it is the one every later phase cites by ID, so
  the size is the point.

## Check yourself

1. The confidence floor appears in several requirements. Which one makes it a *measured* number
   rather than a chosen one, and which experiment supplies it?
2. `NFR-COST-001` says USD 0.02 per child-day. In what sense is that a requirement today, and
   what happens to it in E3?

<details><summary>Answers</summary>

1. `FR-SPC-005`: "its value is the number measured in B3, per engine" — the floor is an output of
   experiment B3, and `FR-LRN-006` / `NFR-*` then apply whatever B3 found.
2. It is a *planning value*: a ceiling the cost model in E3 must be checked against, at list
   prices (`NFR-COST-003`). E3 either confirms a number under it or replaces it with the measured
   ceiling — and the requirement text changes in a revision that cites the experiment.
