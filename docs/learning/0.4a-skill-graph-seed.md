## What was done

The curriculum became data: [skills.v0.1.json](../curriculum/skills.v0.1.json) — three domains,
19 stages, the 28 letters with a default order, nine **per-letter skill kinds**, 76 single nodes
(harakat and long-vowel concepts, 15 discrimination pairs, words, sentences, comprehension,
pre-writing strokes, arithmetic to 100) — 85 authored entries that expand to **328 nodes**.
[check_graph.py](../../lab/0.4-skill-graph/check_graph.py) expands the templates, resolves
three prerequisite forms, proves the graph acyclic, and prints the *frontier* for two example
learners ([results](../../lab/0.4-skill-graph/README.md)). [curriculum/README.md](../curriculum/README.md)
documents the format. Step 0.4 was split: this is the model; 0.4b writes the pedagogy document.

## Topics applied

| Topic | Where | What I already knew it maps to |
| --- | --- | --- |
| A DAG as data: each node lists only what precedes it; order is computed | `skills.v0.1.json` → `prerequisites`; `check_graph.py` → `check_dag()` (Kahn's algorithm) | A dependency graph of packages or build targets, with the same "no cycles" test |
| Templates versus instances | `skills.v0.1.json` → `per_letter` (9 entries) vs `skills` (76); `check_graph.py` → `expand()` | A generic class instantiated per type parameter — nine definitions, 252 objects |
| Threshold prerequisites (`any_of_kind … min`) | `skills.v0.1.json` → `R-H-FATHA-CONCEPT`, `R-F-CONNECT-CONCEPT`, `R-W-3L-HARAKAT`; `check_graph.py` → `resolve()`, `frontier()` | A quorum: "any 3 of these 28", which a plain edge list cannot express |
| The frontier — eligibility computed from state | `check_graph.py` → `frontier()`; results table rows "Frontier …" | A topological "ready set": tasks whose dependencies are done |
| Mastery criteria you can test | `skills.v0.1.json` → `mastery_rules` (`k_of_n`, `min_sessions`), referenced by name | A named policy object instead of a magic number on every row |

| Stage as a label, not a mechanism | `skills.v0.1.json` → `stages`; `curriculum/README.md` | A tag used for grouping in a UI, never for ordering |

## The mental shift

I expected a curriculum to be a list, and a "level" to be a position in it. It is a graph, and a
level is a *view*. The checker made this concrete: a brand-new child is eligible for **30 skills
at once** — every letter's shape, the first stroke, counting to five — because nothing precedes
them. The graph says what is *possible*, never what is *next*. "Next" is a separate, smaller
rule set (the default letter order, the child's name letters first, confusable pairs apart, one
new skill per session), and that rule set is the scheduler Phase 4 will build. Keeping the two
apart is what makes the pedagogy explainable: the prerequisite that unlocked a skill *is* the
sentence the parent reads.

The second shift is about size. The plan said "~120 skills"; the honest number is 85 authored
entries and 328 nodes, because the granularity we chose — harakat as sub-skills per letter —
multiplies by 28. Templates keep the *source* reviewable while letting the *instances* be exact.

## Gotchas hit

- Codes moved from `R-L-SOUND-م` (as written in the design discussion and the smoke doc) to
  `R-L-SOUND-MEEM`. A right-to-left glyph inside a left-to-right identifier renders differently in
  every editor, breaks on this machine's cp1252 console, and is awkward in file names and URLs.
  Unicode letter names are unambiguous and ASCII; the glyph lives in `letters[].glyph`.
- Threshold prerequisites become up to 28 edges each (892 edges in total). Kahn's algorithm is
  fine with that, but a frontier that treated those edges as *hard* requirements would never
  unlock the concept — `frontier()` must count the group and compare with `min`. Two different
  readings of the same edge list; only one is right.
- `print()` of Arabic on this console crashes with cp1252 unless stdout is reconfigured;
  fixed at the source (`sys.stdout.reconfigure(encoding="utf-8")`) rather than with an
  environment variable every run.
- No first-run errors in the graph itself. Suspicious, so I read the frontier lines twice: the
  fatha concept unlocked at exactly three sounds and the per-letter fatha stayed locked — the
  two behaviours that would have exposed a wrong prerequisite form.

## Check yourself

1. A child has mastered the shape and sound of ا، م، س. Which harakat skills are on her frontier,
   and why is «الميم بالفتحة» not among them yet?
2. Why is `stage` not allowed to influence the order in which skills are taught?

<details><summary>Answers</summary>

1. Only `R-H-FATHA-CONCEPT` — its prerequisite is "any 3 `R-L-SOUND` nodes", now satisfied.
   `R-H-FATHA-MEEM` requires both `R-L-SOUND-MEEM` *and* `R-H-FATHA-CONCEPT`; the concept is
   taught once, then each letter's quick node unlocks.
2. Because prerequisites already encode every real dependency; a second ordering mechanism
   would either duplicate them or contradict them. `stage` exists so the parent's dashboard can
   say "she is in the harakat stage: 7 of 11 letters".

</details>
