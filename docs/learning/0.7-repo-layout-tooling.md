# 0.7 — Repo layout & tooling

> **Phase:** 0 · **Kind:** build · **Commit:** `step(0.7): shape the repo — product placeholders, editor/git hygiene, key-less env interface` · **Date:** 2026-09-21

## What was done

Three placeholder folders for the future product — [core/](../../core/README.md),
[child-app/](../../child-app/README.md), [web/](../../web/README.md), each holding one README
that says what will live there and that the name is provisional until Phase 5 — plus four
hygiene files at the root: [.editorconfig](../../.editorconfig) (formatting any editor obeys),
[.gitattributes](../../.gitattributes) (one canonical line ending, binaries marked),
[.gitignore](../../.gitignore) (secrets, audio, recordings, lab outputs, caches) and
[.env.example](../../.env.example) (the committed, key-less interface to the git-ignored `.env`).
Every rule was verified with `git check-ignore -v`, `git check-attr` and a renormalization pass
before being called done.

## Topics applied

| Topic | Where | What I already knew it maps to |
| --- | --- | --- |
| Git tracks file content, not directories — an empty folder cannot be committed | `core/README.md` (and the two siblings) | Why `.gitkeep` files exist in other people's repos; here the placeholder earns its bytes by documenting intent |
| One canonical text form in history (`text=auto` + explicit `eol` pins) | `.gitattributes:4` | Normalizing data at a boundary: store one representation, convert at the edges (checkout) |
| `binary` attribute: no EOL conversion, no text diff/merge | `.gitattributes:19-23` | Declaring a type so generic machinery keeps its hands off — like marking a field opaque |
| Ignore rules as machine-enforced policy, not convention | `.gitignore:8-23` (secrets, audio) | A linter that runs on the *repository*: "recordings never enter git" stops being a promise and becomes a refusal |
| Negated ignore pattern as a documented exception | `.gitignore:10` (`!.env.example`) | Allow-list carved out of a deny-list; the exception is the committed interface |
| `.env` / `.env.example` split | `.env.example` | Config schema committed, config values not — the example file is the *type*, `.env` is the *instance* |
| Editor-agnostic formatting contract | `.editorconfig` | A lint config one level down: enforced by the editor on every keystroke, not by review |

## Experiment

Not a study step — no `lab/` experiment. The verification pass stands in: six ignore probes
matched the intended rule (each traced to its line by `check-ignore -v`), `.env.example`
confirmed *not* ignored, attributes confirmed per file class, and `git add --renormalize .`
staged **zero** tracked files — the new attributes describe the history we already have
rather than rewriting it.

## The mental shift

I had filed `.gitignore` under "housekeeping". Writing it for Nabta showed it is the **first
safety layer the project has** — active before any product code, any validator, any review.
Two product guardrails ("recordings are ephemeral", "no secrets in git") became mechanical
refusals today: a `*.wav` or a `.env` cannot be committed by accident from now on, and that
guarantee cost eleven lines. The same inversion applies to the placeholders: the repo's layout
is itself a document — it records *what the product will be made of* (capabilities → folders)
while refusing to say *what it will be made with* (no manifest, no lockfile, no scaffold).
A repository can hold a promise without holding a decision.

## Gotchas hit

- **Renormalization is a real risk when `.gitattributes` arrives late.** `text=auto` on an
  existing repo can silently mean "every CRLF file is rewritten on next touch", flooding a diff.
  Ran `git add --renormalize .` to force the question — it staged nothing, so history was
  already clean LF. Had it staged files, that rewrite would have needed its own commit, not a
  ride-along in this one.
- **`eol=crlf` on `build.ps1` changes checkouts, not history.** The blob stays LF; the working
  tree gets CRLF on the next fresh checkout on Windows. Nothing to see in this diff — the
  effect is deferred, which is exactly the kind of change worth a note because it will look
  like "nothing happened".
- **`lab/*/out/` vs `lab/**/out/`:** one level of experiment folders is the actual layout, so
  the single-star form was chosen deliberately — a deeper `out/` would *not* be ignored, and
  that surfacing is wanted (an experiment nesting outputs two levels down is drifting from the
  template).
- **The 0.6 note paid off:** `docs/deliverables/.tmp/` (the diagram renderer's scratch folder)
  was recorded as a gotcha last step and became a rule this step. A learning doc that names the
  next step's work is doing its job.

## Check yourself

1. Why do `core/`, `child-app/` and `web/` each contain a README instead of being empty
   folders, and why is creating them now *not* a technology decision?
2. A future experiment produces a 40 KB `ratings.csv` in `lab/2.1-tts/out/` that you want in
   git. What happens on `git add`, and what is the deliberate way in?

<details><summary>Answers</summary>

1. Git stores file content only; an empty directory has none, so it cannot exist in a commit —
   the README is the folder's ticket into history. No technology is decided because the folders
   assert only the capability split from `architecture.md` (tutor core / child experience /
   parent-admin web), and their READMEs say the names are provisional until Phase 5's ADRs.
2. `git add` refuses silently (the path matches `lab/*/out/`). The deliberate way in is
   `git add -f lab/2.1-tts/out/ratings.csv` — the force flag *is* the review moment, as the
   comment at `.gitignore:27-28` documents.
