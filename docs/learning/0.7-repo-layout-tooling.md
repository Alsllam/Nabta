## The mental shift

`.gitignore` is usually housekeeping. In this repo it is the first place the privacy principles
become *enforced* rather than stated: a `.wav` cannot be committed by accident, a `.env` cannot
leak, a provider's raw response in `lab/**/out/` cannot end up in history. The exception path
(`git add -f`, named in a README) is the same shape as the consent path in the product — allowed
only when written down where the rule is. Tooling files are where principles get teeth.

## Gotchas hit

- `.env.*` as an ignore pattern also ignores `.env.example`; the negation `!.env.example` must
  come *after* it. Verifying this produced a second gotcha: `git check-ignore -v` reports a path
  matched by a **negation** pattern as a match, with exit status 0 — my batch check therefore
  claimed a tracked file was ignored. `git check-ignore -v --no-index .env.example` prints
  `.gitignore:8:!.env.example`, and `git add .env.example` succeeds without `-f`: not ignored.
  The exit status of `check-ignore` means "some pattern matched", not "this file is excluded".
- `git add --renormalize .` under the new `.gitattributes` changed nothing beyond the files I had
  edited: the index was already LF because `core.autocrlf` converted on every commit. The
  warnings all day were about *future checkouts*, and `eol=lf` ends them.
- The IDE had auto-generated a `.gitignore` containing only `/.vs`; the pathspec commits of
  earlier steps had left it staged-then-untracked. Replaced by the full file; `.vs/` is still
  covered.
- Placeholder folders need a file to exist in git (git tracks files, not directories) — the
  READMEs are that file, so they were written to say something useful rather than "placeholder".
- `.env.example` names Azure variables because that candidate was agreed; the comment beside
  them repeats the rule that a free candidate is costed at list price and measured beside an
  alternative, so the file cannot be read as a decision.

## Check yourself

1. Why is `*.wav` in `.gitignore` a privacy rule rather than a size rule, and what is the
   documented way to keep one consented sample?
2. `.env.*` is ignored. How does `.env.example` still get committed, and why does the order of
   the two lines matter?

<details><summary>Answers</summary>

1. Recordings are ephemeral by principle P6 (scored, then purged); an audio file in history
   would outlive its time-to-live forever. The exception: `git add -f` plus a line in that
   experiment's README naming the sample and the consent.
2. The negation `!.env.example` re-includes it; git evaluates patterns in order and the last
   match wins, so the negation must follow the pattern it overrides.
